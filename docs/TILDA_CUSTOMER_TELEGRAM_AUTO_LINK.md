# Tilda T706 → персональная Telegram-ссылка после оформления

Дата: 2026-10-14. Реальная корзина Tilda: rec4616518301, проект 12009291, страница 255050809.

## Безопасная схема

1. В браузере при открытии T706 генерируются случайные 32 байта (43 URL-safe символа).
2. Через скрытое поле формы `oms_checkout_nonce_hash` в Tilda отправляется только SHA-256 токена, 64 символа в нижнем регистре. Сам токен не уходит в Tilda.
3. Обычный, уже работающий Tilda webhook передаёт поле Backend вместе с заказом.
4. CRM сохраняет хеш в `DraftOrder.contact_details` внутри одной существующей транзакции создания заявки. Ни ID заказа, ни email, ни телефон не дают доступа.
5. После штатного `tildaform:aftersuccess` браузер POSTит исходный токен в `/integrations/tilda/telegram-link`. Backend сверяет SHA-256 и только после этого выпускает одноразовую ссылку через существующий `DeskService.issue_link`.
6. Клиент открывает Telegram, нажимает Start, бот связывает Telegram ID с конкретным заказом. Переиздание возможно из того же браузера до привязки, после привязки выдача блокируется.

Новый сценарий управляется флагом `TILDA_CHECKOUT_LINK_ENABLED`. По умолчанию выключен. Нет новых SQL-таблиц и миграций. В production не включать до проверки передачи скрытого поля реальной T706.

## Подключение к действующему сайту

После деплоя feature/backend на production добавить в Tilda один тег в Site Settings → More → HTML for HEAD или через T123, доступный на странице заказа и странице успешного оформления:

```html
<script defer src="https://ohmysmell-backend-production.up.railway.app/integrations/tilda/checkout-link.js"></script>
```

Не нужно встраивать секреты API или Telegram-токены в сайт. Не меняйте штатный webhook, корзину, оплату или менеджерский бот. Тег добавляют однократно; скрипт защищён от двойной инициализации. После публикации проверить в браузере, что у T706 формы до отправки появилось скрытое поле с именем `oms_checkout_nonce_hash` и 64-символьным значением. В противном случае не включать флаг: приём заказа продолжит работать, но персональная ссылка не появится.

Для staging-сайта можно использовать URL staging Backend и соответствующее staging Tilda подключение, но не направлять реальные customer orders в staging.

## Проверки E2E

- Оформить новый безопасный заказ на физически доступный товар.
- Проверить, что webhook принят ровно один раз и при повторе не создаёт второй заказ.
- Сверить `oms_checkout_nonce_hash` из Tilda webhook с сохранённым хешем в CRM. Не журналировать браузерный секрет.
- После success увидеть кнопку для Telegram, открыть бота и нажать Start.
- В Telegram клиент видит только свои заявки, а менеджер видит связанного клиента.
- Протестировать переписку, статусы, повторную ссылку после TTL и отказ для чужого токена.
- Перед запуском на production проверить OPTIONS CORS с Origin `https://ohmysmell.ru`, 404 для неизвестного случайного токена и 422 для невалидной длины.
- Проверить, что нельзя получить deep link из одного только номера заявки, телефона или email.

## Ограничения

На странице success Tilda документирует `tildaform:aftersuccess`; совместимость конкретной корзины T706 с динамически добавленным hidden-полем необходимо проверить в реальном опубликованном проекте. Если Tilda не передаёт поле, использовать штатное настроенное скрытое поле T706 с таким же именем и записывать в него хеш скриптом до отправки.

Если клиент ушёл с сайта, не сохранив ссылку и не запустив бота, для удалённого восстановления нужен отдельный подтверждённый канал (например, письмо с одноразовой ссылкой). До подключения такого канала нельзя обещать восстановление после потери браузерной сессии.

- https://help.tilda.cc/forms/webhook (штатный HTTPS webhook)
