# Tilda: SKU и заявленные цены сайта

Изменения предназначены для `feature/sales-core-v2`. Миграция схемы не нужна:
нормализованный Webhook уже хранится в `inbound_messages.body_text`, а новые
служебные поля — в `draft_orders.contact_details` (JSON). Старые заявки автоматически
не изменяются. Внешние идентификаторы и хеш исходного Webhook сохраняются.

## Контракт и ограничения

- SKU берётся из `products[].externalid`; если сайт передаёт `sku`, задайте
  `TILDA_ITEM_FIELD_MAP_JSON={"id":"sku"}` с учётом остальных действующих настроек.
- Точное сравнение с `article` и `code` одновременно, крайние пробелы удаляются,
  **регистр значим**. Имена, fuzzy matching и архивные товары исключены.
- Используется существующий кеш каталога. `MOYSKLAD_CATALOG_CACHE_TTL_SECONDS`
  для Tilda должен быть больше 0 и не больше 300 секунд (по умолчанию 60).
  Просроченный кеш требует успешного обновления. Ошибка оставляет заявку на проверке.
- Цена — положительные целые копейки из нормализованного Webhook. Значения
  `TILDA_PRODUCT_MAP_JSON` и `MOYSKLAD_RETAIL_PRICE_TYPE` этому потоку не нужны.
  Оптовый поток Gmail не изменён.
- Необязательная сумма строки читается из `products[].amount`; путь настраивается
  ключом `total` в `TILDA_ITEM_FIELD_MAP_JSON`. Она проверяется против цены × количества.
- Скидка проверяется арифметически, но любая ненулевая/неизвестная скидка блокирует
  подтверждение. В этой версии нет отдельного механизма согласования/распределения
  скидки по строкам: обычная кнопка подтверждения эту блокировку не снимает.
- Цена Webhook не является независимо проверенной ценой. Финализация требует
  ответственного менеджера, актуальной ревизии и повторной проверки SKU по каталогу.
- Наличие показывается только по успешно полученному текущему полному отчёту
  активных складов. Отсутствующие данные означают «не подтверждено», а не ноль.
  Нулевой остаток не отменяет сопоставление. Отгрузка требует распределённых
  источников либо полученных товаров внешнего поставщика.

## Безопасная проверка заявки №38

Выполнять только в проверенном окружении **backend staging**, с его staging-БД
и `APP_ENV=staging`, `EXTERNAL_WRITES_ENABLED=false`, `TILDA_TEST_MODE=true`,
`ORDER_DESK_SEND_ENABLED=false`. Нужен Telegram ID уже назначенного активного
менеджера и ID разрешённой группы. Утилита не назначает менеджера автоматически.

```powershell
python -m scripts.inspect_tilda_review --draft-id 38 --actor <MANAGER_ID> --chat <GROUP_ID>
```

Утилита только читает БД и каталог МойСклад; показывает ожидаемые SKU, ID товара,
цены в копейках, сумму, проблемы и необходимость изменения. Аудит, outbox,
ревизия и подтверждение не меняются. У неё нет режима применения.
Для DSD020 при переданной цене 1 680 ₽ ожидается `price=168000`.
Фактическая заявка №38 в рамках локальной разработки не проверялась.

После отдельного развёртывания обновлённого manager worker команда
`/sitereprice 38 dry-run` также показывает предварительный результат;
`/sitereprice 38` применяет изменения существующей заявки и пишет аудит.
Она не создаёт новые заявки/заказы/outbox-уведомления. Ответ на новую команду
Telegram отправляется явно; старые сообщения не переотправляются.
Повтор без изменения данных не увеличивает ревизию. Отменённые и финализированные
заявки недоступны. Для старых строк сверяются порядок ID, исходные имена,
количества и SKU; при расхождении операция останавливается.

## Deployment только backend staging

1. Проверить ветку и diff, выполнить `python -m pytest -q`. PostgreSQL-проверки
   запускаются отдельно только в изолированной staging-схеме штатным тестовым runner.
2. После ревью создать локальный коммит; `git push` не требуется. Штатный deploy
   упаковывает **коммит**, а не незакоммиченные изменения.
3. Проверить, что целевой сервис — backend проекта `eloquent-wisdom`, environment
   `staging`; `EXTERNAL_WRITES_ENABLED=false`, `TILDA_TEST_MODE=true`,
   `ORDER_DESK_SEND_ENABLED=false`. Штатный deploy также требует `TILDA_ENABLED=false`
   во время загрузки. Не менять production или флаги отправки старых сообщений.
4. Посмотреть план: `python -m scripts.staging_order_desk_deploy --service backend`.
   После проверки плана выполнить ту же команду с `--execute`.
   Не использовать `--service client`; не развёртывать manager/Gmail workers.
5. Проверить health/readiness backend и выполнить dry-run №38 утилитой выше
   внутри подтверждённого backend staging окружения. Не вызывать submit повторно,
   не запускать outbox retry и не финализировать заявку для smoke test.

Backend-only deployment обновляет приём Tilda. Отдельный manager worker продолжает
использовать прежний код Telegram до собственного последующего deployment; новые
карточки и `/sitereprice` нельзя считать активированными одним backend deployment.
Для отката загрузить предыдущий проверенный коммит только в тот же backend staging.
Схему откатывать не требуется; JSON-поля не удалять.
