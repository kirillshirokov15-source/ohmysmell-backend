# OhMySmell — передача руководителям и запуск без риска учёту

## Карта процессов

**Розничный сайт Tilda:** клиент оформляет заказ на сайте → CRM сохраняет исходные названия, количества и розничные цены → менеджер получает карточку в Telegram → связывает товар с единственной подтверждённой карточкой МойСклад → выбирает источник каждой позиции: собственный склад или склад Х → сборщик подтверждает физически собранный товар.

**Свой склад:** после актуальной проверки остатков формируются складской резерв и отдельная отгрузка по основному складу. **Склад Х (Хатуна):** физическая сборка → одно внутреннее оприходование X по связанным SKU и расчётной себестоимости «цена продажи − 1000 ₽ за единицу» → резерв → отгрузка по складу Х. Нет письма Хатуне, заказа поставщику или обязательств перед Хатуной. Все документы и расходы идентифицированы ключами, повтор при неизвестном результате блокируется до сверки.

**Оптовая почта:** входящие письма по отдельному ящику создают CRM-заявку; темы писем, неточные имена, отсутствие количества, вопросы и подписи проходят разную обработку. Менеджер подтверждает сомнительные товары, количество, контрагента и оптовую цену. Письма-уточнения не являются заказами.

**Buying:** независимое приложение для внешних поставщиков, закупочные цены, импорт прайсов XLSX/CSV, предложения, корзина и закупки. Почта закупок физически и логически отличается от оптового ящика клиентов. Текущие товары Tilda обеспечиваются только своим складом и складом Х; внешний supplier flow через Buying включается отдельно, а не автоматически при каждом заказе сайта.

## Проверка менеджерского бота

- `/emailorders` – заявки оптовой почты.
- `/draft N` – конкретная заявка.
- `/match N ITEM_ID запрос` – повторное сопоставление товара по названию или артикулу; если такого товара в МойСклад нет – вопрос на создание карточки, не автоматическое оприходование.
- `/quantity N ITEM_ID Q REV` – зафиксировать количество после проверки.
- `/cpcheck N` – сверка клиента с актуальным контрагентом в МойСклад.
- `/cpsearch N НАЗВАНИЕ/ИНН` – поиск существующего контрагента.
- `/newcp N ПОЛНОЕ_ЮРИДИЧЕСКОЕ_НАЗВАНИЕ` – проверка дублей, отдельное подтверждение создания.
- `/sources N` – позиции Tilda и их источники.
- `/hatuna N` – отчёт по операциям Х: цена продажи, условная себестоимость, оприходование, резерв и отгрузка (только в конфигурации полной сборки).

## Подключение сотрудников в Telegram-группу

1. Создать закрытую Telegram-супергруппу и добавить туда **существующего менеджерского** Telegram-бота (не клиентского); отключить анонимность администраторов, которые должны управлять заказами.
2. Получить реальный ID группы (отрицательное число вида `-100...`) и положительные Telegram user ID сотрудников. Нельзя брать username вместо числового ID.
3. В Railway **Manager Bot** production установить `MANAGER_TELEGRAM_MODE=group`, `MANAGER_TELEGRAM_CHAT_ID=-100...`, `MANAGER_TELEGRAM_USER_IDS=111,222,...`. Совпадающие `MANAGER_TELEGRAM_CHAT_ID` и `MANAGER_TELEGRAM_USER_IDS` установить также у **Backend, Client Bot и Customer Gmail Worker**, иначе часть клиентских/почтовых уведомлений уйдёт не в ту группу. Список IDs – только подтверждённые сотрудники.
4. Добавить каждому сотруднику запись `managers` (поле `telegram_id`, `is_active=true`) через авторизованную сессию Railway менеджерского сервиса: `python -m scripts.manage_manager_access --telegram-id 111 --name "Фамилия Имя" --production --confirm`. CLI дополнительно сверяет ID со списком Railway. Без записи в CRM доступ не откроется. Убедитесь, что production-сервис имеет доступ к реальной БД и скрипт запускается в его окружении, а не на локальном ПК.
5. Убедиться, что бот имеет право публиковать сообщения в группе. Отправить `/menu` и проверить заказ, кнопки и личные ID двух менеджеров.
6. При увольнении: деактивировать сотрудника `--disable`, удалить его ID из `MANAGER_TELEGRAM_USER_IDS`, затем удалить из группы.

Важно: разрешённые user ID и записи в CRM независимы. Простое добавление человека в группу не даёт прав менять заказы.

## Готовность и границы релиза

- **Production:** Tilda, клиентский бот, менеджерская Telegram CRM, Gmail intake, сопоставление клиентов/товаров, вопросы/заявки, создание контрагента по подтверждению.
- **Интеграционная ветка / безопасный demo:** собственный склад + X, раздельные складские документы и расчётная себестоимость Х, Buying fake email/receipts, отдельная Supplier Gmail обвязка.
- **Не принимать за подтверждённое production:** реальные учётные документы склада Х, автоматическое создание новых номенклатурных карточек отсутствующих товаров, поставщицкая OAuth и живые письма/закупки. Для выпуска требуется отдельный инвентаризационный preflight и проверка одной реальной операции в МойСклад.

Финальный принцип: продажная цена – неизменяемая цена сделки клиента; условная закупочная цена склада Х – отдельное предварительное значение для ежемесячной сверки. Не объединять собственный склад, склад Х и внешний supplier в одном документе.

## Сценарий презентации руководству (до 3 минут)

**Проблема:** заявки приходили через сайт, email и мессенджеры; сотрудники вручную сопоставляли номенклатуру, проверяли клиентов, остатки, собирали закупки и искали переписку.

**Решение:** OhMySmell связывает Tilda, Telegram, CRM, МойСклад и Buying в единый прослеживаемый процесс. Покажите тестовый заказ сайта, как менеджер видит цену, количество, выбирает карточку товара и склад, а сборщик меняет статус. Затем покажите разбор оптового Gmail и сверку контрагента.

**Польза:** меньше ручного переноса данных и двойного ввода, единые карточки, контроль ответственности, история действий, снижение риска двойного оприходования. Buying отдельно собирает закупки и поставщиков.

**Текущий статус:** основные каналы уже функционируют. Склад Х и поставщицкая почта подготовлены на уровне кода и безопасной приёмки, но реальные записи и почтовые отправки ещё защищены выключателями. Это демонстрация пилота, а не обещание полностью автоматического складского production.

**Перед промышленной эксплуатацией:** проверить одну реальную отгрузку со своего склада, одну связку из двух складов и реальное оприходование Х без задвоения; согласовать правила создания отсутствующих SKU; отдельно OAuth и E2E supplier email/Buying.
