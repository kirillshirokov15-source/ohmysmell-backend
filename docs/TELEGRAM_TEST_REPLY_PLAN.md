# Безопасная проверка ответов Client Bot

План для отдельного согласования. Никакие настройки и данные этим документом не меняются.

## Что происходит при отключённой отправке

При `ORDER_DESK_SEND_ENABLED=false` ответы сохраняются в `desk_messages` со статусом
`pending`. Worker отправки не запускается; `run_once` возвращает управление до
изменения очереди. Повторный update не создаёт второй ответ. После включения
отправки накопленные сообщения, попавшие в разрешённую область, могут быть отправлены.

## Ограниченный тест без старых уведомлений

1. Оставить отправку выключенной. Проверить staging, identity Client Bot,
   `EXTERNAL_WRITES_ENABLED=false` и единственный разрешённый ID тестового клиента.
2. Зафиксировать начало теста UTC. Клиент отправляет новые `/start`, `/status`,
   `/status 36` (последнее только если заявка принадлежит этому клиенту).
3. Read-only проверить новые строки очереди: `direction=to_customer`, точный
   `destination`, `kind=client_menu`, `status=pending`, `attempts=0`, отсутствие
   `telegram_message_id`, время после начала теста и соответствующие
   `source_message_id`. Зафиксировать только ID этих ответов; не включать старые
   уведомления, ответы других клиентов или строки `sending`/`uncertain`.
4. После отдельного разрешения изменить переменные **только Client Bot**:
   `ORDER_DESK_STAGING_CLIENT_RECIPIENT_IDS=<один согласованный ID>`,
   `ORDER_DESK_STAGING_MESSAGE_IDS=<точный список новых ID>`,
   `ORDER_DESK_STAGING_DRAFT_IDS=` (пусто). Существующую корректную границу
   `ORDER_DESK_STAGING_NOT_BEFORE` можно сохранить. Пока оставить отправку выключенной.
   Проверить эффективные переменные после разрешения ссылок Railway.
   Области message IDs и draft IDs объединяются через OR: непустая область заявок
   может разрешить дополнительные сообщения. Время NOT_BEFORE не ограничивает
   явно разрешённые message IDs, поэтому проверка их возраста обязательна.
5. Только после проверки очереди и отдельного согласования включить
   `ORDER_DESK_SEND_ENABLED=true` у Client Bot с перезапуском worker.
   Никакие команды изменения Railway сейчас не выполняются.
6. Проверить, что только выбранные ответы получили `sent`, по одной попытке и
   Telegram receipt; остальные строки не изменились. Повторный update/перезапуск
   не должен повторять отправку. Новые неразрешённые ответы останутся `pending`.
7. Вернуть отправку в `false`; убрать разрешённые message IDs, не расширяя область
   заявок и не меняя других сервисов. Не сбрасывать статусы/attempts/receipts и не
   выполнять массовый retry. Неопределённый результат требует ручной сверки.

## Выпуск кода отдельно от включения отправки

После локального коммита этих исправлений подставить его полный SHA:

```powershell
.venv\Scripts\python -m app.scripts.staging_bots_release --commit <FULL_SHA>
# Только после подтверждения deployment:
.venv\Scripts\python -m app.scripts.staging_bots_release --commit <FULL_SHA> --execute
```

Скрипт выпускает оба staging-бота из одного коммита последовательно, сохраняет
переменные и останавливается при частичном сбое. Включение клиентской отправки
не является частью выпуска. Миграция не нужна.

Manager хранит указатель на inline-меню в памяти текущего worker, отдельно для
бота, группы, темы и сотрудника. Повторные и одновременные вызовы используют это
меню. После полного перезапуска worker первое обращение создаст новую пару
сообщений; история и старые карточки сохраняются. Устойчивое хранение меню не
добавлялось, чтобы не менять PostgreSQL или инфраструктуру.
