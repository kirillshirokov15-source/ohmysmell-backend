## Обнаруженные и исправленные дефекты

1. **Отгрузка обычного заказа не перепроверяла источник после сборки.** Проверка
   выполнялась только на `assembling`, а на `shipped` — только для Tilda.
   Регрессии для OWN и X падали с `DID NOT RAISE OperationError`.
   Исправление в `OrderOperations.act`: проверять обеспечение при любой отгрузке.
   После исправления все три новые сценария и весь PostgreSQL-набор проходят.
2. **Устаревший HTTP assertion** в PostgreSQL-сценарии Tilda ожидал 202 вместо
   действующего контракта 200. Исправлен тест, поведение API не изменено.
3. **Устаревший lifecycle-тест Tilda** ожидал отгрузку без источника. Теперь он
   проверяет блокировку, затем явно создаёт синтетическое распределение внутри
   тестовой схемы для проверки последующих карточек, уведомлений и доставки.
   Это не реализация production-процесса назначения источников Tilda.
4. **Неполный штатный runner** не включал `test_order_desk_hardening_postgres.py`.
   В список добавлены этот файл и новые регрессии обеспечения.

При повторном запуске в уже использованной схеме обнаружены коллизии фиксированных
Telegram update ID в старых тестах. Это ограничение воспроизводимости тестового
набора, не ошибка рабочих данных. Для финального результата создана **новая**
схема и выполнен полный runner. Перед каждым полным повтором запускать валидатор,
а не повторно использовать старый `validation.json`.

## Что ещё не реализовано / блокирует полный production

1. **Обеспечение Tilda до отгрузки.** При финализации `manual_fulfillment` не
   вызывается `capture_order_supply`; не создаются procurement/settlement/plans.
   `FulfillmentService.plan()` отклоняет Tilda. Без отдельного разрешённого процесса
   назначения и подтверждения источников финальная отгрузка заблокирована.
   Безопасная блокировка работает, но сквозной сценарий Tilda не завершён.
2. **Живые закупки и оприходование МойСклад.** `FakeProcurementAdapter` возвращает
   `fake-order:*` и `fake-receipt:*`. `DisabledMoySkladProcurementAdapter` блокирует
   живую запись. OWN/X используют чтение существующих остатков, а не собственный
   процесс создания приходного документа. Такие операции в этой приёмке не
   реализовывались и не проверялись на реальном МойСклад.
3. **Живая отправка закупок поставщику.** `DisabledGmailSupplierSender` требует
   адаптер сверки неопределённых результатов и не отправляет письмо даже при
   включении флагов. `requested` в ProcurementService означает ручное действие.
4. **Связь Buying с обеспечением клиентского заказа.** Получение отдельной Buying
   purchase не является автоматически получением `ProcurementRequest` конкретной
   строки клиентского заказа. Общий каталог переиспользуется, но эти процессы
   разделены. Сквозная автоматическая связь не заявляется готовой.
5. **Резервирование.** Складской план распределяет прочитанный остаток, но не
   создаёт внешний резерв. Тест не доказывает защиту от конкурирующего расхода
   реального остатка другими заказами/системами. Для production нужна согласованная
   процедура резерва и сверки фактического исполнения.
6. **Согласование скидок Tilda** и **разрешение продажи X ниже базы** не имеют
   отдельных завершённых процессов; текущие блокировки не снимаются автоматически.

Новых неисправленных падений в выполненном PostgreSQL-наборе нет. Перечисленные
функциональные пробелы остаются блокерами полного запуска. Production-подключения,
реальные платежи, отправки и документы не проверялись: разрешение на запуск
production из этого отчёта не следует.

## Воспроизведение безопасного прогона

Запустить отдельный локальный PostgreSQL только на loopback. Для каждой попытки
создавать новую схему штатным валидатором. В PowerShell, в процессе тестирования:

```powershell
$env:STAGING_DATABASE_URL='postgresql://oms_test@127.0.0.1:55439/postgres'
$env:DATABASE_URL='postgresql://unused:unused@127.0.0.1:1/never_connect'
$env:EXTERNAL_WRITES_ENABLED='false'
.\.venv\Scripts\python.exe -m scripts.validate_staging
# Продолжать только после успешного завершения валидатора:
.\.venv\Scripts\python.exe -m scripts.run_staging_tests
```

Изменения переменных выше относятся только к процессу PowerShell, не к Railway.
Не использовать live-e2e/deploy/resume-скрипты для этой приёмки. Кластер с trust-auth
предназначен только для синтетических локальных данных и после тестов останавливается.
