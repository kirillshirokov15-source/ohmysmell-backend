# Назначение источников Tilda

Реализовано локально в `feature/sales-core-v2`. Продолжает архитектуру существующих
`Shipment`, `WarehouseAllocation`, `OrderEvent`, `BuyingPurchase`, `BuyingEvent`
и `XSettlement`; новых таблиц складского учёта или отдельной корзины не добавлено.
Розничные цены Tilda, количества строк заказа и оптовые цены Gmail не пересчитываются.

## Работа менеджера

После подтверждения заявки использовать **номер созданного заказа**, а не заявки.
Операции доступны назначенному активному менеджеру в разрешённой группе.

```text
/sources ЗАКАЗ
/sourceadd ЗАКАЗ РЕВИЗИЯ ПОЗИЦИЯ КОЛИЧЕСТВО own СКЛАД
/sourceadd ЗАКАЗ РЕВИЗИЯ ПОЗИЦИЯ КОЛИЧЕСТВО partner_x СКЛАД ПОСТАВЩИК БАЗА_КОП
/sourceadd ЗАКАЗ РЕВИЗИЯ ПОЗИЦИЯ КОЛИЧЕСТВО external СКЛАД OFFER_ID
/sourceaction ЗАКАЗ РЕВИЗИЯ НАЗНАЧЕНИЕ receive
/sourceaction ЗАКАЗ РЕВИЗИЯ НАЗНАЧЕНИЕ post_receipt
/sourceaction ЗАКАЗ РЕВИЗИЯ НАЗНАЧЕНИЕ cancel
```

`/sources` показывает ID позиций/назначений, количество, источник, склад,
готовое к сборке количество, статус плана и связанной закупки Buying. Назначения
также видны в обычной карточке заказа. Каждое действие увеличивает `order.revision`.
Отмена источника и изменение распределения разрешены до начала сборки.

Одна строка может быть разбита на несколько количеств: например, 8 единиц —
2 OWN/склад 1, 1 OWN/склад 2, 1 X/склад 1, 1 X/склад 2 и 3 у внешнего поставщика.
Сумма назначений не может превысить количество строки. Необязательно назначать
всё одним действием, но неполное обеспечение блокирует сборку и отгрузку.

| Источник | При назначении | Что требуется до сборки/отгрузки |
|---|---|---|
| OWN | Проверяются активный товар, склад и текущий доступный остаток; учитываются локальные распределения | Явное назначение менеджером подтверждает источник |
| X | Фиксируются партнёр, количество и базовая стоимость; используется существующий `x_calculation`/`XSettlement` для части строки | `receive`, затем `post_receipt` |
| Внешний поставщик | По действующему `SupplierOffer` создаётся обычный черновик `BuyingPurchase` с неизменяемым снимком количества и закупочной цены | Отправка и получение в Buying, затем `receive` и `post_receipt` назначения |

Для внешнего источника нужны активное предложение на тот же товар, достаточное
заявленное количество (если указано), активный поставщик с email и настройка этого
поставщика/валюты в Buying. Общая корзина Buying не меняется. Создание покупки
переиспользует тот же helper, что и обычный checkout. Клиентские контакты и розничные
цены не передаются в supplier snapshot. Получение Buying-покупки без явной связи с
назначением не обеспечивает клиентский заказ.

Состояния назначения: `awaiting_receipt → received → confirmed`, либо `cancelled`.
Для OWN начальное состояние — `confirmed`. **Черновик закупки, отправленная
закупка и просто полученный товар не равны оприходованному товару.**

При отмене назначения его ещё не отправленная Buying-покупка отменяется в той же
транзакции. Уже отправленная/полученная покупка сохраняется для сверки; отмена
назначения не означает возврат товара или отмену письма поставщику. При отмене
всего заказа отменяются его назначения/планы и неотправленные связанные покупки.
Ранее созданные финансовые снимки X сохраняются: для действующих обязательств
нужно учитывать состояние связанного назначения и плана.

## API

Существующий internal supply API расширен:

```text
GET  /internal/supply/orders/{order_id}/sources
POST /internal/supply/orders/{order_id}/sources
```

Нужны `X-Internal-API-Token`, `X-Manager-Telegram-Id` и назначение этого менеджера
ответственным. Пример атомарного назначения нескольких частей:

```json
{
  "action": "assign",
  "expected_revision": 0,
  "idempotency_key": "unique-operation-key",
  "parts": [
    {"item_id": 101, "qty": 2, "source_type": "own", "warehouse_id": "warehouse-a"},
    {"item_id": 101, "qty": 1, "source_type": "partner_x", "warehouse_id": "warehouse-b", "supplier_id": 12, "base_cost_minor": 100000},
    {"item_id": 101, "qty": 3, "source_type": "external", "warehouse_id": "warehouse-a", "offer_id": 34}
  ]
}
```

Числа в примере условные. Для остальных действий вместо `parts` передаётся
`allocation_id`. Ответ содержит `order_id`, `revision`, `items`, `allocations`.
Повтор того же ключа/содержимого/менеджера возвращает сохранённый результат;
актуальное состояние после последующих операций нужно читать GET-запросом.
Telegram использует ID команды для ключа повторной обработки.

## Согласованность с существующими планами и Buying

- Строка заказа блокируется `FOR UPDATE`, версия проверяется до изменения.
  Аудит использует прежний уникальный `(order_id, idempotency_key)`.
- OWN-назначения разных заказов сериализуются PostgreSQL advisory lock по товару
  и складу. Учитываются уже распределённые количества. Обычный автоматический
  `FulfillmentService` использует те же ключи блокировки и вычитает новые явные
  назначения Tilda; прежняя логика ценообразования не меняется.
- Создание, получение и отмена черновика Buying используют прежнюю блокировку
  workspace. Конкурентные отправка/отмена не превращают черновик в «полученный».
- Проверка перед сборкой и отгрузкой суммирует только подтверждённые назначения
  из действующих планов. `cancelled`, `uncertain`, `exporting` не дают готовности.
  Полное количество каждой строки должно быть обеспечено.
- Отменённый план не оживляет старые количества при новом назначении: прежние
  части остаются отменёнными. После начала сборки изменять источники нельзя;
  выявленная позднее проблема с планом блокирует отгрузку и требует разбора.
- Частичные получения моделируются отдельными назначениями соответствующих
  количеств. Одно назначение подтверждается целиком.

## Миграция

`q60ec754da87_tilda_source_allocations.py`, после `p59db643bc76`.

Обоснование: прежний unique `(shipment_id, order_item_id)` не позволял разделить
строку между источниками на одном складе, а `XSettlement` допускал лишь один
снимок на строку. Добавлены поля источника/получения/связи Buying к существующим
allocations и `allocation_id` к XSettlement. Для прежних записей уникальность
сохранена частичными индексами. Для новых частей связь Buying уникальна, поэтому
одна покупка не может обеспечить несколько назначений повторно.

Старые значения заказа, цены, количества, идентификаторы, финансовые снимки не
переписываются. Прежние складские записи имеют `managed_source=false`; сами по себе
они не становятся подтверждением источника Tilda. Миграция проверена на новой
локальной схеме; отдельная проверка старой синтетической схемы сохранила все прежние
значения 43 таблиц, включая 25 заказов. Реальные №38/№16 не использовались.

Автоматический downgrade после появления новых назначений запрещён: обратное
схлопывание нескольких источников в одну строку привело бы к потере данных.
Применение миграции к рабочим окружениям в этой задаче не выполнялось.

## Реальный API и симуляция

| Действие | Текущее состояние |
|---|---|
| Чтение каталога, складов и остатков МойСклад | Существующий read-only адаптер используется при OWN-назначении. В тестах ответы подменены |
| Выбор источников, проверка количеств, планы, версии, аудит, связь Buying | Реальные локальные транзакции БД; не создают документы МойСклад |
| Отправка закупки в Buying | Существующий `simulate_send`, без реального письма/заказа поставщику |
| Получение Buying-покупки | Локальная отметка и fake receipt существующего адаптера |
| Получение и оприходование X/внешнего назначения | Явная симуляция: `receipt_simulated=true`, `simulated-receipt:allocation:<id>` |
| Отгрузка | Локальный переход состояния после проверки источников; не документ отгрузки МойСклад |

Симулированные поступления запрещено использовать в production; при
`APP_ENV=production` либо включённых внешних записях они не дают готовности.
Получение/оприходование в этих режимах отклоняется. `EXTERNAL_WRITES_ENABLED=false`
остаётся обязательным для текущего полного сценария с X/внешними товарами.

Готовы для подключения существующего **read-only** API проверка товара/склада и
наличия. Для будущих записей подготовлены локальные связи, идемпотентность и аудит,
но это не готовый live receipt/export adapter: нужны реальные документы получения,
сверка неопределённых результатов, привязка внешних ID и согласованное резервирование.
Существующие блокировки экспорта Tilda не сняты. Одного переключения флага недостаточно.

OWN-назначение — локальное удержание, не резерв МойСклад. Оно консервативно не
освобождается при симулированной отгрузке, поскольку внешний остаток не списан.
Отмена освобождает количество. Автоматическая сверка локальных удержаний с реальными
резервами/списанием остаётся задачей подключения live API. Ранее существовавшие
автоматические планы между собой сохраняют прежние правила; эта доработка не
заявляет глобальный внешний механизм резервов для всех каналов.
